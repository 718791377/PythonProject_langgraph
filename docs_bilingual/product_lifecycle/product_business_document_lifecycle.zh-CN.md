# 产品与商业文档生命周期

本文定义商业、互联网、产品、平台和工具链工作的通用 0-8 文档栈。它不绑定具体产品，也不绑定任何单一项目管理来源。它解释每个阶段回答什么问题、需要哪些输入、使用哪些工具与技术，以及输出哪些可交付结果。

本文采用过程组式写法：每个层级都分成“输入”、“工具与技术”、“输出”三类。

- 输入：该层级接收的外部输入、项目外部约束，以及来自其他层级的输入。
- 工具与技术：该层级在分析、判断、设计或交付过程中使用的方法、文件、检查方式和治理技术。
- 输出：该层级最终形成的可交付结果，既可以对外发布，也可以传递给其他层级继续使用。

这些规则是通用治理叠加层。它们不替代白皮书、BRD、MRD、北极星 Plan、PRD、技术设计、implementation plans、OpenSpec 或仓库 checker，而是帮助这些文档按生命周期保持输入、处理和输出一致。

## 快速区别：白皮书 vs 北极星 Plan

| 文档 | 核心问题 | 主要作用 | 典型读者 | 执行角色 |
| --- | --- | --- | --- | --- |
| 白皮书 | 为什么这个方向成立？ | 改变认知，并建立新叙事 | 决策者、合作方、未来维护者 | 它论证方向，但不是任务计划 |
| 北极星 Plan | 如何获胜并衡量进展？ | 把战略变成可量化系统 | 建设者、维护者、操作者 | 它指导阶段规划，但仍高于 implementation tasks |

白皮书论证一个新方向是真实且有价值的。北极星 Plan 定义长期目标、核心指标、输入指标、杠杆和分阶段靠近目标的路径。

## 生命周期通用裁剪规则

不同项目不需要一次性写满所有文档。应按风险、不确定性、影响范围和交付方式选择最小充分文档集。

- 预测式门禁适合需求清晰、风险较高、需要显式 release evidence 或 rollback evidence 的工作。
- 适应式切片适合需求不清楚、需要用户反馈、需要 spike、MVP 或小型实验的工作。
- 混合式方式适合仍要探索，但最终交付必须经过评审、测试、发布和复盘门禁的工作。

## 0. 认知叙事层

核心问题：这件事为什么存在？

### 输入

- 行业趋势、技术趋势、政策环境、用户行为变化或组织战略变化。
- 现有方案缺口、重复失败案例、长期摩擦和结构性痛点。
- 商业层、市场层或技术层发现的反复问题；这些下游反馈可反向触发新的认知叙事。

### 工具与技术

- 趋势分析：把外部变化整理成未来几年可能发生的方向。
- 问题建模：把表面需求还原成结构性矛盾、约束和机会。
- 叙事推演：说明为什么现有方案不足，以及新范式为什么可能成立。
- `whitepaper.md` 是白皮书文件；它解释行业趋势、结构性痛点、现有方案为什么不够，以及新范式是什么。

### 输出

- 白皮书或认知说明，用于说明方向为什么值得理解和讨论。
- 新范式定义、核心假设、证据链和非目标边界。
- 向商业层输出“是否值得进一步评估”的方向候选。

## 1. 商业层

核心问题：这件事值不值得做？

### 输入

- 认知叙事层输出的方向候选、问题定义和核心假设。
- 组织目标、预算边界、资源约束、合规约束和经营优先级。
- 市场层提供的用户规模、竞品证据和付费意愿信号。

### 工具与技术

- 商业模式分析：判断价值如何转化为收入、成本节省、效率提升或风险降低。
- 收益与成本估算：比较开发、运行、模型、维护、合规、获客和迁移成本。
- 市场规模估算：TAM 是总市场，SAM 是可服务市场，SOM 是可触达市场。
- 单位经济模型：CAC 是获客成本，LTV 是用户生命周期价值，ROI 是投入产出比。
- `brd.md` 是商业需求文档；它解释商业目标、收入逻辑、成本结构和投入产出。

### 输出

- BRD、商业假设、投资边界和成功标准。
- 做、不做、推迟，或继续研究后再决定的商业决策。
- 向市场层输出目标人群和价值假设，向战略层输出商业目标和约束。

## 2. 市场层

核心问题：用户到底需要什么？

### 输入

- 商业层输出的目标人群、价值假设和商业约束。
- 外部用户访谈、问卷、竞品观察、渠道反馈、客服反馈和使用数据。
- 认知叙事层提出的问题框架，以及产品层或增长层回传的真实使用摩擦。

### 工具与技术

- 用户分层：识别目标用户、影响者、付费者和操作者。
- 场景分析：描述用户什么时候、为什么、在什么约束下需要方案。
- 痛点分析：把功能请求背后的真实问题提炼出来。
- 竞品分析：比较替代方案、差异化机会和进入门槛。
- 反馈循环：用小样本验证、原型反馈或 MVP 反馈降低不确定性。
- `mrd.md` 是市场需求文档；它把市场证据和用户需求转化为产品方向。

### 输出

- MRD、目标用户、目标场景、市场切入位置和竞品差异化判断。
- 用户问题清单、优先级信号和进入策略。
- 向战略层输出市场机会，向产品层输出用户场景和需求证据。

## 3. 战略与北极星层

核心问题：我们如何获胜？

### 输入

- 认知叙事层输出的新范式和长期假设。
- 商业层输出的商业目标、成本边界和成功标准。
- 市场层输出的用户场景、需求证据、竞品差异和切入策略。
- 技术层输入的能力边界、风险约束和可行性反馈。

### 工具与技术

- 北极星指标设计：选择最能代表用户价值和长期进展的唯一指标。
- 输入指标拆解：定义能够驱动北极星指标的前置指标。
- 杠杆识别：找出产品、技术、流程、分发或运营机制中最能改变结果的动作。
- 阶段裁剪：按风险和不确定性选择预测式、适应式或混合式推进方式。
- `north_star_plan.md` 是北极星 Plan；它定义核心指标、输入指标、增长或能力杠杆和阶段路径。

### 输出

- 北极星 Plan、阶段路径、优先级逻辑和非目标边界。
- MVP 定义；MVP 是最小可验证产品或最小可验证能力，用于验证关键假设。
- release train 定义；release train 是按固定节奏推进版本发布的计划方式。
- 向产品层输出范围优先级，向执行层输出阶段门禁和路线图约束。

## 4. 产品层

核心问题：产品应该做成什么样？

### 输入

- 战略层输出的北极星指标、阶段路径、优先级逻辑和非目标边界。
- 市场层输出的用户分层、场景、痛点和需求证据。
- 技术层输出的可行性边界、接口约束、安全约束和成本约束。
- 增长层或复盘层回传的采用摩擦、反馈总结和实验结果。

### 工具与技术

- 用户流程设计：把用户目标拆成进入、操作、反馈和完成路径。
- 信息架构设计：组织内容、页面、对象和动作。
- 原型验证：用低保真或高保真原型确认交互和布局是否可理解。
- 优先级排序：按价值、风险、成本和依赖关系划分 P0、P1、P2。
- 验收标准设计：把功能需求转化为可测试、可评审的结果。
- `prd.md` 是产品需求文档；它把战略转化为面向用户的功能、流程、优先级和验收标准。
- `user_journey.md` 是用户旅程文档；它展示用户使用产品前、中、后的完整体验。
- `information_architecture.md` 是信息架构文档；它展示内容、页面和动作如何组织。
- `prototype.fig` 或其他原型文件是设计原型；它在设计工具中展示预期交互和布局。

### 输出

- PRD、用户旅程、信息架构、原型和验收标准。
- 产品本阶段做什么、不做什么，以及哪些需求进入后续阶段。
- 向技术层输出系统需求来源，向执行层输出可拆解的功能范围。

## 5. 技术层

核心问题：技术上如何安全实现？

### 输入

- 产品层输出的 PRD、用户流程、验收标准和范围边界。
- 战略层输出的阶段约束、长期演进方向和非目标边界。
- 外部技术约束，包括安全、隐私、性能、成本、兼容性、部署环境和供应链限制。
- 执行层、增长层或复盘层回传的缺陷、性能瓶颈、运维摩擦和技术债。

### 工具与技术

- 架构设计：拆分模块、接口、数据流、状态边界和信任边界。
- 风险分析：识别安全、隐私、可用性、成本、可维护性和迁移风险。
- 质量门禁：定义测试、审查、回滚、可观测性和兼容性要求。
- 构建与采购判断：判断是自研、复用、购买、集成还是推迟。
- `srs.md` 是系统需求规格；它定义系统级功能需求和非功能需求。
- `trd.md` 是技术需求或技术设计文档；它解释所选技术方案和权衡。
- `hld.md` 是高层设计；它定义主要模块、信任边界、数据流和集成点。
- `lld.md` 是低层设计；它定义具体组件、脚本、函数、schema 和边界情况。
- `api_spec.md` 是 API 规格；它定义输入、输出、权限、错误和兼容性。
- `data_model.md` 是数据模型；它定义实体、字段、关系和持久化规则。

### 输出

- SRS、TRD、HLD、LLD、API 规格、数据模型和风险控制说明。
- 系统可以被构建、测试、运行、审查和回滚的技术证据。
- 向执行层输出实施边界、依赖关系、测试要求和发布风险。

## 6. 执行层

核心问题：如何交付？

### 输入

- 产品层输出的范围、优先级、验收标准和非目标边界。
- 技术层输出的设计、接口、依赖、风险控制和测试要求。
- 战略层输出的阶段路径、发布节奏和成功标准。
- 外部输入，包括团队容量、时间窗口、发布限制、审批限制和运营窗口。

### 工具与技术

- 工作拆解：把范围拆成可验证、可回滚、可审查的小切片。
- 计划冻结：在实施前冻结关键设计、任务清单、验收标准和风险边界。
- 变更控制：通过 OpenSpec、代码审查、CI、测试和发布门控制范围漂移。
- 监控与控制：在实施中跟踪进度、风险、缺陷、依赖和验收状态。
- `implementation_plan.md` 是实施方案；它把某个已选阶段拆成可执行工作。
- `tasks.md` 是任务清单；它跟踪具体步骤和完成状态。
- `test_plan.md` 是测试计划；它定义单测、集成测试、端到端测试、人工检查和回归检查。
- `release_plan.md` 是发布计划；它定义上线时机、发布门和沟通方式。
- `rollback_plan.md` 是回滚计划；它定义如何回到安全的前一个状态。

### 输出

- 可执行任务、测试计划、发布计划、回滚计划和交付证据。
- 已实现、已验证、已发布或可发布的工作结果。
- 向增长层输出可采用能力，向复盘层输出交付记录、问题记录和经验素材。

## 7. 增长与采用层

核心问题：它如何变得更大、更有用或被更多项目采用？

### 输入

- 执行层输出的已发布能力、发布记录、已知限制和采用入口。
- 战略层输出的北极星指标、输入指标和增长杠杆。
- 市场层输出的用户分层和渠道信号。
- 复盘层输出的经验教训、反馈总结和实验结果。

### 工具与技术

- 路线图规划：按用户价值、商业价值、技术依赖和风险安排后续版本。
- 增长实验：用小实验验证获客、激活、留存、收入或采用机制。
- 指标体系：把 DAU、MAU、留存、转化、CAC、LTV、质量或采用指标定义清楚；DAU 是日活跃用户，MAU 是月活跃用户。
- 采用分析：记录系统在哪里被使用、为什么被使用，以及还剩哪些摩擦。
- `roadmap.md` 是产品路线图；它定义后续版本和优先顺序。
- `growth_plan.md` 是增长计划；它定义获客、激活、留存、收入或采用机制。
- `metrics.md` 是指标文档；它按需要定义 DAU、MAU、留存、转化、CAC、LTV、质量或采用指标。
- `adoption_report.md` 是采用报告；它记录系统在哪里被使用，以及还剩哪些摩擦。

### 输出

- Roadmap、增长计划、指标体系、采用报告和后续版本候选。
- 系统扩展、采用、优化或商业化的路径。
- 向战略层反馈指标进展，向产品层反馈需求变化，向复盘层输出实验和采用证据。

## 8. 复盘与学习层

核心问题：它是否有效？下一轮应该改什么？

### 输入

- 执行层输出的交付记录、测试结果、发布结果、缺陷记录和事故记录。
- 增长层输出的指标结果、采用报告、实验结果和用户反馈。
- 市场层、产品层、技术层回传的重复问题、未满足需求和技术债。
- 外部输入，包括客户反馈、审计结论、合规变化和运营事件。

### 工具与技术

- 复盘分析：识别发生了什么、为什么发生、影响范围、修复动作和预防动作。
- 实验分析：比较不同方案的效果，并判断是否继续、停止或扩大。
- 经验沉淀：把事件、交付和反馈转化为可复用规则、模板、检查项或后续任务。
- 关闭门禁：确认交付物、文档、发布状态、回滚证据和经验教训已经归档。
- `post_mortem.md` 是事故或项目复盘；它记录发生了什么、为什么发生、影响、修复和预防。
- `ab_test_report.md` 是 A/B 测试报告；它比较不同方案，并解释哪个效果更好。
- `feedback_summary.md` 是用户反馈总结；它捕获重复出现的用户反应和请求。
- `lessons_learned.md` 是经验教训文档；它把经验转化为可复用规则或后续任务。

### 输出

- 复盘报告、实验报告、反馈总结、经验教训和治理更新建议。
- 下一轮要继续、停止、扩大、重构或废弃的明确判断。
- 向认知叙事层、商业层、市场层、战略层、产品层、技术层和执行层反馈可复用经验。

## 按项目规模选择最小文件集

小型内部工具通常需要简短北极星说明、PRD、技术设计、implementation plan、test plan 和 retrospective。implementation plan 是实施方案，用来把已选阶段拆成可执行工作；test plan 是测试计划，用来定义验证方式；retrospective 是复盘记录，用来沉淀经验。公共产品、商业产品或长期平台应该补齐白皮书、BRD、MRD、roadmap、metrics 和 release governance。roadmap 是路线图，用来安排后续版本；metrics 是指标文档，用来定义衡量方式；release governance 是发布治理，用来定义上线门禁和回滚要求。

项目越影响金钱、用户、信任、合规或长期平台行为，这套文档栈就越应该显式化。
