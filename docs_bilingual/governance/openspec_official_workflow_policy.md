# OpenSpec Official Workflow Policy

## 1. Purpose

This document defines how this repository keeps its workflow aligned with the currently installed official OpenSpec CLI.

For this repository, official OpenSpec workflow governance applies at the project-level handoff layer:

- user-level shared runtime and control surfaces may be reused across many projects on the same machine
- repo-local source, repo-local durable truth, and repository-scoped structural change remain authoritative inside this repository
- structural changes that affect that handoff must enter OpenSpec here rather than being hidden only in user-level assets

## 2. Authority Order

Authority order:

1. official OpenSpec upstream behavior and documentation
2. the locally installed official OpenSpec CLI and the managed instructions it generates for this repository
3. repository-level workflow policy and governance documents

## 3. Startup Entry

- New sessions start from `docs_bilingual/project_startup_summary.zh-CN.md` and `docs_bilingual/project_startup_summary.md`
- `AGENTS.md`, OpenSpec governance docs, stable specs, and active changes are downstream reads chosen from that startup-summary-first intake
- No repository-local shortcut should silently replace that startup-summary-first order

## 4. Required Bootstrap Or Refresh

- Install the official CLI package when `openspec` is not already available: `npm install -g @fission-ai/openspec@latest`
- Run `powershell -ExecutionPolicy Bypass -File .\tools\bootstrap-official-openspec.ps1` after cloning into a real git repository, after switching AI tools, after upgrading the OpenSpec CLI, or when the repository-local official instruction surface needs refresh
- For Codex, the bootstrap script must materialize the current official Codex integration for this repository instead of relying on hand-written slash-command descriptions

## 5. Default Official Lifecycle

- Use the current OpenSpec command surface generated by the installed CLI for the active AI tool
- Create or refine a change proposal before implementation
- Inspect active work with `openspec list --json`, `openspec status`, `openspec show`, and `openspec validate`
- Implement only after the required change artifacts are ready
- Archive completed changes with `openspec archive <change> --yes` only after implementation, specs, and validation are stable
- Do not archive code-class changes as documentation-only closeout. A code-class change is any change marked `x_change_class: code`, `runtime`, `mixed`, `tooling`, or `ci`, or any archived change whose artifacts describe runtime, scripts, helpers, tests, checkers, guards, CI, or code behavior. Such changes must land source, executable check, CI, or test evidence in the same branch before archive.
- For this repository, archives that affect code, executable checks, CI, stable specs, startup instructions, repository instruction surfaces, or structural governance rules additionally follow the local archive-worktree isolation flow in `docs_bilingual/governance/openspec_opsx_project_usage_policy.md` - governance policy for repository OPSX routes and archive workflow gates. This local flow does not change the official semantics of `openspec archive <change> --yes`, the official OpenSpec CLI command that archives a completed change.
- Do not invent repository-local aliases that override official OpenSpec command semantics
- When a structural change affects repo-local source, repo-local durable-state contracts, or the project-level handoff from shared user-level surfaces into this repository, treat that change as OpenSpec work in this repository

## 6. Experimental Workflow Rule

- Experimental OpenSpec workflows may be used only when all of the following are true:
  - the upstream official documentation still describes that workflow
  - the locally installed CLI explicitly supports or generates that workflow for the active AI tool
  - the repository intentionally opts into that workflow
- If any of those conditions fail, fall back to the default official lifecycle

## 7. Enforcement

- `python .\tools\run_openspec_guard.py --root .` is the reusable local enforcement entry point
- `python .\tools\verify_official_openspec.py --root .` must pass before this repository is treated as fully initialized for official OpenSpec workflow enforcement
- `openspec validate --all` must pass before structural OpenSpec work is treated as complete
- `tools/check_name_clarity_rules.py` is the local strict name-clarity checker; it blocks bare script, path, command, variable, or profile list items when run through `python .\tools\run_openspec_guard.py --root .`
- `--no-baseline` is the strict checker mode used by the guard; it disables compatibility allowances so current and future findings block local enforcement.
- `tools/check_openspec_code_archive_evidence.py` is the local code-archive evidence checker; it blocks code-class OpenSpec archives when the current branch diff contains no source, executable check, CI, or test evidence.
- `openspec validate --all` remains the official OpenSpec CLI validation command; it does not enforce this repository-local name-clarity rule by itself
- Install `.githooks/pre-commit` with `powershell -ExecutionPolicy Bypass -File .\tools\install-git-hooks.ps1` after `git init` or after cloning an existing repository into real git history
- Keep at least one supported CI guard surface in the repository, such as `.github/workflows/openspec-guard.yml` or `.gitlab-ci.yml`
- If the hosting provider supports required-status checks, mark the OpenSpec guard job as required so merges do not depend only on local self-discipline

The JSON contract for repository check scripts and the aggregated guard report is defined in:

- `docs_bilingual/governance/openspec_check_and_guard_json_output_policy.md` - governance document that defines JSON output contracts for repository checks and the aggregated guard report.

## 7A. Governance Bilingual And Encoding Rule

For governance artifacts under `docs_bilingual/` and `openspec/`:

- maintain an English `.md` primary and a Chinese `.zh-CN.md` companion together once that authority surface is bilingual
- treat the English `.md` file as the normative primary and keep its body text ASCII
- save the Chinese companion as UTF-8
- read the Chinese companion through an explicit UTF-8 path first before considering any fallback diagnosis or repair path

## 8. Allowed Exceptions

- one-off runtime investigation
- temporary log inspection
- narrow bug confirmation with no structural change
- minor documentation correction with no policy or workflow impact
