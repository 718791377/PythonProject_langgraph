## 1. Relationship Model And Naming Boundary

### 1.1 `General` vs `General_2`

- `PythonProject_General` is the fuller governance template. It may include reusable docs and source templates for oh-my-codex, native_omx, LangGraph compatibility, MCP-scope policy, launcher-payload policy, local/remote gate parity, and generated-project durable-state scaffolding.
- `PythonProject_General_2` is the local-only template. It must remain local Git + OpenSpec + Superpowers + native Codex subagents only.
- Neither template may copy `D:\PythonProject_langgraph` live `.omx/state/`, selectors, worktree claims, runtime logs, current mainline facts, credentials, or user-specific absolute paths as defaults.

### 1.2 Comet / OpenSpec / Superpowers

- OpenSpec owns WHAT: proposal, design constraints, capability specs, tasks, validation, and archive.
- Superpowers owns HOW: brainstorming, planning, execution discipline, TDD/debugging/review, and verification-before-completion.
- Comet coordinates the five-stage control loop: Open -> Design -> Build -> Verify -> Archive.
- Comet is not a native subagent, oh-my-codex, native_omx, LangGraph, or durable-team backend. References to `/comet` in the template must keep that boundary explicit.

### 1.3 Optional orchestration product-line assumptions

General may document the Codex orchestration product line as a reusable assumption set:

- native Codex remains the base layer;
- oh-my-codex is an additive workflow layer;
- native_omx is the worker-centric durable lane;
- LangGraph is the graph-shaped durable orchestration lane;
- one durable task uses one backend family at a time;
- durable teams are threshold-gated and are not auto-launched at template startup.

These are templateable governance assumptions, not evidence that a generated project already has a running team or ready LangGraph backend.

## 2. Goals And Non-Goals

### 2.1 Goals

- Provide a reusable cold-start read order and task-specific policy routing for new projects.
- Provide OpenSpec + Superpowers + Comet governance documents and sample change scaffolding.
- Provide CI/MR gate scripts whose JSON output shape can be reused locally and remotely.
- Provide MCP-scope and launcher-payload guidance that is safe on Windows and avoids long inline startup payloads.
- Provide optional LangGraph compatibility/orchestration source templates while keeping official `langgraph` installation user-level.
- Provide generated-project durable-state rules: `.omx/state/` may be created by the hydrated project at runtime but must not be copied from this repository.
- Provide checkers that fail closed on unresolved placeholders, missing bilingual pairs, malformed native agent TOML, and local/remote gate drift.

### 2.2 Non-Goals

- Do not clone `D:\PythonProject_langgraph`.
- Do not install or modify user-level Codex configuration, global pip/npm/Git config, browser config, or credentials.
- Do not copy `.git/`, `.venv/`, `node_modules/`, `.env`, caches, tokens, runtime logs, or `.omx/state/`.
- Do not implement business application code, GUI flows, browser automation, remote publication, or a persistent team runtime in Phase 0.
- Do not push remotes or create GitLab/GitHub MR/PRs from this template update.

### 3.1 Startup authority

Generated projects own their own `docs_bilingual/project_startup_summary.md` and `.zh-CN.md`. The template may define a reusable read order, but it must not copy this repository's current read order as a live fact. Context-retention sentinel rules may be referenced, but literal sentinel prompt text belongs only in the generated project's startup summary pair.

### 3.2 OpenSpec and Comet assets

General should create a local OpenSpec skeleton and a template-safe example change. It must not copy active or archived changes from this repository. Example artifacts must be marked as examples and safe to delete after project initialization.

### 3.3 MCP and launcher payload assets

MCP documentation must distinguish:

- Codex-direct project tools;
- shared MCP Router tools;
- tools that do not belong in either by default.

Launcher documentation and helpers must prefer short file-backed payload references over long inline `-c developer_instructions=...` arguments.

### 3.4 Optional orchestration assets

General may include optional profile docs for oh-my-codex, native_omx, and LangGraph. These docs must distinguish `installed`, `enabled`, `selected`, and `ready` states and must not claim that a generated project has selected or launched durable orchestration.

### 3.5 LangGraph compatibility source and state

- Official `langgraph` package: user-level shared installation, not vendored into the template.
- `tools/langgraph_durable_orchestrator/`: repo-local compatibility/orchestration source that may be templated.
- `.omx/state/langgraph/`: generated-project runtime state only; ignore or create on demand after project hydration.

### 3.6 CI/MR parity

Local CI, local MR review, and remote CI/MR must call the same manifest-driven scripts. Remote configuration may install prerequisites and invoke the shared script, but it must not maintain a divergent checker sequence.

## 4. Comet / OpenSpec / Superpowers Contract

- Every substantial template update starts with an OpenSpec change unless explicitly classified as a small tweak/hotfix.
- Comet state is governance metadata for the change, not durable runtime state for the generated project.
- Superpowers planning must produce task-level implementation slices with files, steps, validation, and rollback.
- Archive closes the OpenSpec loop only after verification evidence exists.
- This plan is a source-repository plan; target-template execution still needs a target-repository precheck and target-local OpenSpec change.

## 8. Rollback And Cleanup

- Revert document mistakes with a local Git revert and rerun `git diff --check` plus OpenSpec guard.
- In `D:\PythonProject_General`, use local Git to revert target-template mistakes; if uncommitted, restore by the `git status --short` file list.
- Keep failed hydration temporary directories and JSON reports for diagnosis until the root cause is fixed.
- Revert only template `tools/langgraph_durable_orchestrator/` source or docs for LangGraph template mistakes; do not delete user-level official `langgraph` installs.
- Revert launcher/helper generation logic for payload mistakes; do not mutate user-level launchers or global Codex configuration.
- Do not delete remote branches, push remotes, or edit protected remote settings as part of this Phase 0 rollback.

## 9. Risks And Default Decisions

- Risk: template docs accidentally inherit live facts. Default: use placeholders and target-local probes, never copy runtime state.
- Risk: LangGraph appears enabled by documentation alone. Default: describe optional profile states and require readiness checks.
- Risk: local and remote gates drift. Default: remote CI calls the local manifest-driven gate.
- Risk: Windows command-line payloads exceed limits. Default: use file-backed instruction payloads.
- Risk: Chinese docs become mojibake through terminal copy/paste. Default: write/read UTF-8 files directly and validate source text, not console rendering.
