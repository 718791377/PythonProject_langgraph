## Context

The global automatic collaboration policy is now a user-level governance rule: qualifying tasks should automatically evaluate experts, durable workflow, and persistent team without the operator repeating prompt phrases. However, several user-level docs are managed/generated by `tools/install-codex-user-level-team-mode.ps1`. Manual edits under `C:\Users\lenovo\.codex\...` can therefore be overwritten by a future installer refresh unless the same wording is embedded in the repository source templates and validated by tests/checkers.

Current constraints:

- Native `spawn_agent` remains subject to the platform/tool contract. This change cannot bypass that contract; it can only force correct routing evidence and fallback behavior.
- Startup itself still must not auto-launch a durable team. Durable/persistent teams remain threshold-gated by frozen plan plus independent slices, or stabilization blockers.
- The main Codex CLI session remains the leader for activation checks, fan-in, and release decisions.

## Goals / Non-Goals

**Goals:**

- Make "automatic collaboration is the default" durable across regenerated user-level docs and startup model-instruction payloads.
- Keep the correct blocker vocabulary for native subagent platform constraints: `experts=blocked:platform_subagent_invocation_constraint`.
- Extend checker and installer tests so generated docs and launcher instructions cannot regress to missing-reminder based routing.
- Preserve the distinction between candidate/selected/running collaboration surfaces and threshold-gated durable-team launch.

**Non-Goals:**

- Do not force durable/persistent teams for small single-slice tasks.
- Do not bypass native `spawn_agent` platform/tool invocation constraints.
- Do not change user-level capability switch semantics.
- Do not mutate user-level config files such as `config.toml`.

## Decisions

### Decision 1: Put the rule in generated assets, not only live user files

`Get-TeamPlaybookContent`, `Get-TeamQuickReferenceContent`, `Get-TeamLeaderTomlContent`, and the startup model-instructions generator will carry the rule. This prevents later installer refresh from erasing the policy.

Alternative considered: keep only manual edits in `C:\Users\lenovo\.codex`. Rejected because managed files are explicitly regenerable and may be overwritten.

### Decision 2: Checker-backed phrases are stable ASCII tokens

The checker will require stable strings such as `Automatic collaboration is the default`, `platform_subagent_invocation_constraint`, and forbidden missing-reminder language. These tokens are easy to assert across English, bilingual, and generated surfaces.

Alternative considered: rely on semantic review. Rejected because this boundary must survive cold starts and context loss.

### Decision 3: Keep spawn-agent constraint as a blocker, not a reason to skip collaboration

Generated guidance will state that platform/tool subagent constraints must be reported as `experts=blocked:platform_subagent_invocation_constraint`, then continue with eligible durable lanes or main-session takeover.

Alternative considered: phrase it as requiring explicit user request for subagents. Rejected because the user-level rule explicitly forbids missing-reminder reasons.

## Risks / Trade-offs

- **Risk:** The added startup guidance increases instruction size. → **Mitigation:** Use concise repeated bullets and stable tokens rather than long prose.
- **Risk:** Manual user-level edits can still drift before reinstall. → **Mitigation:** Repository templates and tests are the source of truth; already-created `.bak.<timestamp>` files allow live-file rollback.
- **Risk:** The policy could be mistaken as automatic team launch. → **Mitigation:** Keep threshold language next to the default rule and preserve no-autolaunch startup boundaries.
- **Risk:** Platform `spawn_agent` restrictions remain. → **Mitigation:** Report concrete blocker and route to durable lane or main-session takeover instead of pretending expert work ran.

## Migration Plan

1. Update repository source templates and governance docs.
2. Extend tests/checkers.
3. Run targeted validation and guard.
4. After local validation, reinstall or refresh user-level assets from the updated installer if needed.
